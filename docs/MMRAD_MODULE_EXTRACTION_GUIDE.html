Cómo extraer el módulo MMRAD

Mapa verificable para trasladar el acceso a radiología desde HHR a otra aplicación local, manteniendo búsqueda por RUT, informes estructurados, PDF, comprobante y acceso DICOM sin exponer credenciales en el navegador.

1. Alcance mínimo que debe conservarse

Incluido

  • Abrir el visualizador con un paciente ya seleccionado por RUT.
  • Buscar todos los estudios o filtrar por fechas.
  • Agrupar por modalidad y priorizar CT en la presentación.
  • Abrir PDF mediante un proxy autenticado.
  • Abrir el comprobante en una vista HTML saneada.
  • Abrir el visualizador DICOM ofrecido por MMRAD.
  • Extraer y copiar hallazgos e impresión de informes CT.

No trasladar como acoplamiento

  • La tabla completa del censo ni sus contextos React.
  • Credenciales reales, cookies de sesión o RUT de pacientes de ejemplo.
  • Dependencias de Eloísa: MMRAD es una integración serverless independiente.
  • La estética exacta de HHR si la aplicación destino tiene su propio sistema visual.

Regla de seguridad: MMRAD_USERNAME y MMRAD_PASSWORD existen sólo en el proceso servidor. Nunca usar prefijo VITE_, nunca serializarlas y nunca enviarlas al cliente.

5. Flujos e interacciones

A. Acceso directo desde una fila

  1. La fila verifica nombre, documento RUT chileno y validez del RUT.
  2. El clic detiene la propagación para no activar otros controles de la fila.
  3. Se monta el modal de forma diferida con un único objeto paciente.
  4. initialPatientRut selecciona el paciente y autoSearchInitialPatient inicia una sola consulta.
  5. Si la identidad de la fila cambia, se cierra la superficie para impedir mostrar datos del paciente anterior.

B. Búsqueda en el RIS

  1. El frontend obtiene el token Firebase actual.
  2. La función valida origen, método, Bearer, rol y rate limit.
  3. El backend lee los secretos, abre la portada Liferay y conserva cookies sólo en memoria.
  4. Localiza dinámicamente las acciones de login y búsqueda.
  5. Publica el RUT; interpreta filas HTML y normaliza enlaces.
  6. Para estudios CT con informe HTML, descarga y estructura título, técnica, antecedentes, hallazgos e impresión.

C. Acciones de un examen

  • Ver PDF: abre primero una ventana vacía para respetar el gesto del usuario; descarga por proxy; usa URL blob; intenta imprimir y revoca la URL.
  • Comprobante: descarga por proxy, elimina scripts/eventos/botones de impresión y muestra una previsualización.
  • DICOM: abre el enlace HTML5 devuelto por el RIS; mantenerlo como navegación explícita, no incrustarlo sin revisar CSP.
  • Copiar informe: sólo se habilita cuando existen secciones estructuradas.

6. Dependencias y seguridad

Dependencias de runtime

  • Node.js 22.
  • React, TypeScript y lucide-react para UI.
  • Firebase cliente para obtener ID token.
  • Firebase Admin en backend para autorizar roles.
  • Netlify Functions o servidor Node compatible con su handler.
  • fetch, TextDecoder('latin1') y Buffer.

Controles obligatorios

  • Secretos sólo en servidor.
  • Lista explícita de roles autorizados.
  • CORS por origen permitido, no comodín.
  • Rate limit antes de contactar al RIS.
  • Timeout y reintento acotados.
  • Sin RUT, nombres, enlaces ni informes en logs/telemetría.
  • Sanitización antes de renderizar HTML remoto.

Fragilidad conocida: MMRAD es un portal Liferay sin API formal en este módulo. Cambios en formularios, columnas, etiquetas o codificación HTML pueden romper el parser. Mantener fixtures anonimizados y pruebas del contrato.

7. Plan de extracción recomendado

  1. Copiar primero los tipos y controladores puros. Hacer pasar sus pruebas sin React ni red.
  2. Definir un puerto cliente. Por ejemplo RadiologyGateway.search/pdf/receipt; la UI no debe conocer Netlify.
  3. Portar el backend. Mantener login, cookies, latin1, normalización y parser sin simplificaciones prematuras.
  4. Adaptar autenticación. Si la app ambulatoria usa Firebase, reutilizar Bearer y roles; si no, reemplazar ambos lados del contrato.
  5. Portar el servicio frontend. Cambiar sólo la URL base o inyectar el gateway.
  6. Portar el modal. Sustituir BaseModal, estilos y runtimes del navegador por equivalentes.
  7. Agregar el disparador ambulatorio. Construir paciente desde el RUT del episodio/atención, no desde texto visible.
  8. Validar localmente con proxy serverless. Una SPA servida sólo por Vite no ejecuta mmrad-search.
  9. Probar una búsqueda, PDF, comprobante y DICOM con datos autorizados del entorno de prueba.

Recomendación: extraer por contratos, no convertir de inmediato en paquete npm. Primero demostrar el módulo dentro de la aplicación ambulatoria; empaquetarlo sólo cuando haya dos consumidores estables.

8. Ejecución local segura

# .env.local — valores omitidos intencionalmente
MMRAD_USERNAME=<secret-server-only>
MMRAD_PASSWORD=<secret-server-only>

# La URL funcional es la del proxy serverless, no el puerto Vite interno.
netlify dev --offline --functions netlify/functions --target-port 3000 --port 8888
# abrir: http://localhost:8888/census
  • El origen local debe estar permitido por isOriginAllowed.
  • La cuenta Firebase debe existir en el entorno correspondiente y tener un rol autorizado.
  • Un 401 sin Bearer confirma que la función existe, no que las credenciales RIS funcionen.
  • La prueba completa exige una solicitud autenticada que termine en HTTP 200 y resultados visibles.

Criterios de aceptación refutables

  • Un clic desde una atención abre el paciente correcto y busca una sola vez.
  • Cambiar de atención no conserva resultados del paciente anterior.
  • Una cuenta sin rol recibe 403; sin sesión recibe 401.
  • Los secretos no aparecen en bundle, red del navegador, logs ni repositorio.
  • Fechas ISO se convierten al formato esperado por el RIS.
  • El cambio de HTML del portal falla de forma visible y no inventa resultados.
  • PDF y comprobante se obtienen por proxy autenticado.
  • El HTML remoto se sanea antes de mostrarse.
  • Timeout, reintento y rate limit están cubiertos.

10. Instrucción breve para la IA implementadora

Migra el módulo MMRAD desde HHR hacia la aplicación local de atenciones ambulatorias. Conserva el backend como frontera de secretos, la autorización por Bearer/rol, el login Liferay con cookies efímeras, el parser y los proxies de PDF/comprobante. Adapta únicamente el modelo de paciente y el sistema visual. Implementa acceso directo por RUT con una sola búsqueda automática, cierre por cambio de identidad y pruebas equivalentes a las listadas. No copies credenciales, datos clínicos reales, contextos del censo ni dependencias de Eloísa.
