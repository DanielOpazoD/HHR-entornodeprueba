1. Resumen y alcance

Este documento describe lo observado en las aplicaciones, lo implementado en el repositorio y las reglas explícitas que conectan Rayen con HHR.

Confirmado

Visible en sesión autenticada actual o respaldado directamente por código y pruebas.

Inferido

Conclusión técnica razonable desde assets, rutas o comportamiento, pero no contrato oficial.

Pendiente de validar

Necesita caso clínico controlado, datos reales no sensibles o acceso al entorno institucional.

Evidencia histórica

Observación previa y fechada. Puede cambiar y debe revalidarse antes de decidir.

Qué es cada superficie

  • Ficha Médico: ficha clínica hospitalaria, listas de encuentros, episodios, indicaciones, registros médicos y de enfermería.
  • Hospitalizado / Gestión de Camas: ocupación y estados de camas, solicitudes de ingreso, egresos administrativos, listas de trabajo e informes.
  • Extensión Centro HHR: capa MV3 que agrega herramientas clínicas, reutiliza sesiones oficiales y sirve de puente controlado hacia HHR.
  • HHR: censo local y sistema de continuidad hospitalaria que reconcilia datos de Eloísa, exige revisión y persiste con la sesión Firebase del usuario.
  • Syslab: portal interno de laboratorio consultado directamente desde la LAN para el visor de exámenes.

Principios que no deben romperse

  • La ausencia en Ficha Médico no es autoridad de egreso.
  • Una cama ocupada en HHR nunca debe sobrescribirse silenciosamente.
  • El modo por defecto es preview con confirmación humana.
  • Tokens y datos clínicos temporales deben minimizarse y no persistirse innecesariamente.
  • Las escrituras clínicas solo se declaran exitosas después de releer y verificar Eloísa.
  • La navegación entre pacientes invalida acciones ligadas al episodio anterior.
Alcance epistemológico. No existe documentación oficial completa de Rayen dentro del repositorio. Los nombres de endpoints y estructuras son contratos observados por la integración; pueden cambiar sin aviso. Toda mejora debe fallar de forma conservadora y conservar una ruta de validación en sesión real.

3. Ficha Médico

Superficie principal donde vive el Centro HHR y desde la cual se obtiene el censo clínico normalizado.

Sesión observada

Huella frontend actual

  • Aplicación Next.js con chunks bajo /_next/static/ y App Router.
  • Idioma del documento: español.
  • Rutas de trabajo conocidas: /dashboard/encounter-list, variante de enfermería /dashboard/encounter-list-nurse y episodio como último segmento numérico.
  • La extensión observa pushState/replaceState, pageshow, foco y visibilidad para revalidar sesión y contexto.

Flujo visible de la lista

  • Vistas confirmadas: pacientes sin médico, interconsultas, pacientes propios y pacientes egresados de alta.
  • Filtros visibles: nombre/RUN y servicio.
  • La barra Centro HHR se inserta en la franja superior, ajusta su posición al encabezado real y se vuelve flotante en pantallas pequeñas.
  • En una ruta sin episodio, Lab queda deshabilitado y las operaciones masivas siguen disponibles.

Lectura del censo

1

Vincular sesión

/api/auth/session entrega una identidad clínica reducida: establecimiento, profesional, rol e identidad visible. Si el token cambia o la sesión expira, se invalida la vinculación anterior.

2

Resolver contexto médico o de enfermería

La ruta y el rol determinan qué lista consultar. Una URL médica antigua nunca debe reutilizarse después de pasar a enfermería.

3

Obtener encuentros

En contexto médico se usa filterType=3 para censo activo completo y filterType=2 como señal de egresados. En enfermería se unen y deduplican las listas noveltyNurseList, uneventfulNurseList e incomeNurseList.

4

Enriquecer por episodio

Se consulta encabezado/demografía y diagnóstico principal activo, con techo de seis operaciones concurrentes para no generar ráfagas contra Ficha Médico.

5

Normalizar

La extensión produce un RayenCensusSnapshot desacoplado del JSON crudo, con episodio, RUN, nombres separados, nacimiento, sexo/género, servicio, habitación, cama, ingreso, diagnóstico/CIE-10 y señales clínicas.

Regla de completitud. isComplete=true solo es válido después de ensamblar el censo completo. Si el snapshot es parcial, HHR no puede inferir nada desde ausencias.

4. Hospitalizado · Gestión de Camas

Segunda sesión Rayen, usada como autoridad administrativa y fuente de reportes hospitalarios.

Sesión observada

Huella frontend actual

  • SPA con router hash y raíz #app.
  • Bundles visibles: /manifest.js, /vendor.js y /app.js.
  • Rutas confirmadas: #/bed, #/work_list y #/reports.
  • Navegación visible: Gestión de camas, Lista de trabajo, Mantenedor e Informes.

Funciones visibles

  • Resumen de camas por estados: disponibles, reservadas, ocupadas, altas médicas, altas de enfermería y bloqueadas.
  • Acciones como bloquear cama y registrar solicitud de ingreso.
  • La extensión no debe automatizar estas acciones; hoy usa Hospitalizado como fuente autorizada de sesión, lookup e informes.

Conexión temporal desde Centro HHR

  1. El usuario abre una ventana oficial de Hospitalizado desde Conexiones.
  2. El login ocurre directamente en Rayen; la extensión no recibe la contraseña.
  3. El script MAIN observa el token que la propia app agrega a sus requests y lo vincula a un connectionAttemptId.
  4. El relé entrega al service worker token, base API, establecimiento y metadatos mínimos.
  5. La sesión reducida queda en chrome.storage.session y la ventana temporal puede cerrarse.
  6. Olvidar borra la sesión. Una expiración o identidad incompatible debe degradar el estado a no conectado.
Autoridad administrativa. Solo el informe masivo “Lista de Pacientes con Alta Administrativa” puede crear en HHR un alta, traslado o CMA estadístico. Alta médica, cierre de enfermería o desaparición del listado son señales, nunca orden para vaciar una cama.

Detalles de receta

  • La receta completa sigue siendo el Jasper oficial Reporte_Receta_Medica.pdf.
  • El formato compacto total deriva del mismo PDF y preserva encabezado, orden/hora, despacho, prescriptor, RUN del profesional, fecha, folio e “impreso por”.
  • La receta por profesional agrupa fármacos activos por autor y deduplica por MRE_ID; no inventa un folio.
  • La validación por profesional se cruza con el historial del episodio y mantiene un respaldo temporal cuando corresponde.
  • Las recetas externas se separan por medicamento activo; no contaminan el PDF oficial combinado.

Protocolo de escrituras clínicas

UI → solicitar opciones y permiso vigente
UI → enviar comando con episodio, instrumento y payload validado
Worker → registrar generación protegida y ejecutar escritura oficial
Worker → GET de verificación exacta en Eloísa
UI ← resultado verificado | ambiguo | rechazado
UI → ACK solo después de presentar el resultado
Recuperación → espera mínima + revisión explícita + segundo GET concordante
No confundir éxito HTTP con éxito clínico. Un 2xx o una respuesta ambigua no basta. El estado “Sincronizado en Eloísa” exige lectura posterior verificable y concordancia con la generación protegida.

6. Laboratorio Syslab

Nuevo módulo nativo de la extensión que traslada las capacidades centrales del visor HHR a Ficha Médico, sin scraper externo.

PR #85

Entrada y búsqueda

  • Solo disponible con episodio numérico activo.
  • Obtiene RUN e identidad desde el encabezado oficial de Eloísa.
  • Abre el portal oficial http://10.4.69.90/syslab/ para login realizado por el usuario.
  • Lista informes por fecha, hora, origen y exámenes; permite filtrar y seleccionar hasta 24 por análisis.
  • Puede abrir el PDF autenticado sin sacar el documento de la sesión local.

Salida clínica

  • Tabla longitudinal de variables por fecha.
  • Unidades, referencias y alertas numéricas o cualitativas fuera de rango.
  • Tendencias numéricas con cada valor rotulado; máximo de 24 tendencias prioritarias.
  • Vista completa por informe y copia tabulada al portapapeles.
  • Normalización de alias frecuentes: leucocitos, plaquetas, PCR, nitrógeno ureico, HCO3, T4L, triglicéridos y HbA1c.

Pipeline directo en la extensión

1

Buscar por RUN

syslab-bridge.js navega la sesión oficial y extrae órdenes. La lista se sanea, ordena y limita.

2

Validar identidad

El cuerpo del RUN debe coincidir en todas las filas y luego dentro de cada informe. No se acepta un lote mixto.

3

Obtener detalle

Se procesan tres informes en paralelo, con timeout de 30 s por request y límite de 6 MB por cuerpo.

4

Extraer y parsear

Si llega PDF, PDF.js extrae texto localmente. Si llega HTML, el bridge resuelve el contenido o PDF anidado. El parser detecta secciones y hallazgos numéricos/cualitativos.

5

Construir análisis

lab-viewer.js genera columnas, comparación, tendencias, informes y resumen de conteos. Cualquier detalle faltante, duplicado, con error o RUN distinto invalida el lote.

Riesgo de infraestructura conocido. Syslab se sirve por HTTP dentro de la LAN. La extensión mantiene el tráfico dentro del equipo/red clínica y no envía resultados a HHR, pero HTTP no cifra frente a otros actores de la red. HTTPS en Syslab sigue siendo la corrección recomendada.

7. Sincronización con HHR

La extensión produce evidencia; HHR decide, reconcilia y persiste. Esa separación es deliberada.

Contrato implementado

Flujo principal

1

Health handshake

HHR pregunta si la extensión, Ficha Médico y Gestión de Camas están disponibles. Los estados son independientes: ready, stale o missing.

2

Snapshot

El botón Sincronizar Eloísa solicita el censo. La extensión responde con el contrato normalizado o un error sanitizado.

3

Planificar diff

HHR cruza por clinicalEpisodeId y, como fallback, por RUN. Produce ingresos, actualizaciones, movimientos de cama, egresos, conflictos y pendientes administrativos.

4

Conciliar autoridad de egreso

Se solicita el informe de Gestión de Camas para D a D+1 y se aplican reglas de fecha insular, traslado, fallecimiento y CMA.

5

Preview o automático

preview es el default y requiere confirmación. auto solo aplica sin revisión si no hay conflictos, altas pendientes, egresos desconocidos ni correcciones de días previos.

6

Aplicar defensivamente

Siempre parte del registro más fresco. Una cama ocupada no se pisa; la operación se omite y queda reportada. Los movimientos históricos son idempotentes.

7

Persistir con autoridad HHR

La app guarda mediante sus casos de uso y sesión Firebase, pasa validación Zod y usa la cola/outbox con políticas de retries, conflicto y telemetría.

8

Enriquecimiento clínico

Después del censo puede consultar signos vitales, dispositivos, escalas/CUDYR y panel clínico. Es bajo demanda o efímero según el dato; nunca debe disfrazar un fallo parcial como vacío.

Resultado de reconciliación

OperaciónSignificadoProtección

updatesMismo episodio/RUN y misma cama, con cambios de campos clínico-demográficos permitidos.No reemplaza datos fuera del contrato de importación.

Reglas de camas y CMA

  • Habitacion N + Cn se mapea a H{N}C{n}.
  • Recuperacion k o Rk se mapea a cama UTI Rk.
  • Neo k se mapea a NEOk.
  • CMA es un tipo de egreso, no una cama paralela. CMAR1 ocupa R1; CMAN1 ocupa NEO1.
  • La clasificación CMA requiere origen exacto CMA, ingreso y egreso el mismo día y ausencia de traslado/fallecimiento que determine otra categoría.
Trazabilidad sin PHI. rayenSyncHistory conserva actor, tiempos, salud de fuentes y agregados del diff/cobertura. No guarda nombres, RUN, diagnósticos ni errores crudos; mantiene como máximo 20 eventos por día.

Reglas del protocolo

  • Cada request asíncrono debe llevar reqId o una identidad/generación equivalente.
  • Todo listener debe comprobar event.source === window y, cuando corresponde, el origen.
  • Los objetos que cruzan mundos se reducen a la forma mínima necesaria.
  • Los timeouts terminan en error explícito, no en colección vacía que parezca válida.
  • Las rutas de episodio aceptan solo IDs numéricos y preservan variante médica/enfermería.

10. Seguridad, privacidad y límites

Controles existentes y amenazas que una IA debe tener presentes al modificar la extensión.

Controles existentes

  • Host permissions limitadas a superficies Rayen, Syslab, localhost y HHR testing.
  • Token vinculado a identidad; 401/403 invalida sesión.
  • Validación de episodio numérico y origen oficial antes de navegar o consultar.
  • Selecciones por lotes con expiración y revalidación.
  • Bloqueo fail-closed de documentos parciales y lotes Syslab incompletos.
  • Vendors PDF/XLS vendorizados, versionados y verificados por SHA-256.
  • Historial operativo y errores sanitizados sin PHI.

Riesgos que siguen abiertos

  • Cambios silenciosos de endpoints o formas JSON de Rayen.
  • Rutas SPA o cabeceras visuales que cambien y desplacen la barra.
  • Syslab sobre HTTP en LAN.
  • Tokens de sesión con vida mayor a la UI que los originó.
  • Ambigüedad temporal de egresos entre día local y fecha impresa.
  • Controles clínicos visibles para un rol sin autorización efectiva.
  • Reintentos que dupliquen una escritura si se debilita el protocolo ACK/recovery.

Huella pública histórica separada

26 junio 2026 Una revisión pasiva anterior observó que la raíz de Ficha Médico redirigía a autenticación y presentaba CSP; también confirmó que el ecosistema Rayen/Eloísa mezcla tecnologías y subdominios. Esa evidencia es contextual, no reemplaza la inspección autenticada actual y no debe reutilizarse como afirmación permanente.

Política para pruebas. Usar lectura y cuentas/casos dummy autorizados. No probar escrituras destructivas, altas, bloqueos de cama, eliminación ni cambios clínicos sobre pacientes reales. Para verificar una escritura, usar el flujo oficial, payload controlado y trazabilidad completa.

11. Runbook para otra IA

Secuencia recomendada para navegar, diagnosticar o mejorar sin perder contexto clínico.

A. Orientación inicial

  1. Leer extension/README.md, extension/manifest.json y este documento.
  2. Confirmar rama/worktree activo, versión del manifest y que la extensión cargada corresponde a esa carpeta.
  3. Verificar las tres fuentes por separado: Ficha Médico, Gestión de Camas y Syslab.
  4. Clasificar la tarea: UI insertada, bridge, worker, parser, sincronización HHR o infraestructura.
  5. Determinar si el flujo es solo lectura o escritura clínica; las escrituras requieren controles adicionales.

B. Navegación de Ficha Médico

  • En lista médica, identificar si se está en /dashboard/encounter-list; en enfermería, preservar encounter-list-nurse.
  • No inferir episodio desde texto visual; usar el segmento numérico validado de la URL.
  • En rutas sin episodio, esperar que Lab y acciones de paciente actual estén deshabilitadas.
  • Después de transición SPA, comprobar que el modal anterior quedó invalidado antes de actuar.
  • Usar atributos estables de la extensión: #hhr-clinical-operations-bar, labels ARIA y data-encounter-id.
  • No depender del orden de botones de Rayen ni de nombres de clases minificadas.

D. Norma para implementar mejoras

  1. Escribir primero el contrato puro: forma de entrada, salida, validación y errores.
  2. Mantener la lógica clínica testeable fuera de background.js cuando sea posible.
  3. Agregar el mínimo permiso de host/recurso y registrarlo en manifest.
  4. Crear UI con semántica, ARIA, foco restaurable y estados loading/empty/error/partial.
  5. Invalidar el estado al cambiar episodio, sesión o identidad.
  6. Probar shape inesperado, timeout, 401/403, duplicados, datos parciales y navegación rápida.
  7. Ejecutar release check, tests focalizados y prueba visual autenticada antes del PR.

13. Pruebas y gates

La extensión tiene pruebas unitarias específicas y un gate estructural de release.

Comandos mínimos

npm run check:rayen-extension-release
npm run typecheck
npx vitest run src/tests/rayen-import/
npx vitest run src/tests/services/laboratory/ src/tests/features/laboratory/
npm run test:e2e:laboratory-smoke

Qué valida el release check

  • Manifest V3 y archivos declarados.
  • Host permissions y recursos accesibles.
  • Sintaxis de scripts operativos.
  • Versiones/licencias/hashes SHA-256 de vendors.
  • Registro temprano de PDF/XLS compatible con service worker MV3.

Matriz manual autenticada

  • Lista médica: Centro HHR visible, Lab deshabilitado sin episodio y health listo.
  • Lista enfermería: contexto correcto sin reutilizar URL/token médico obsoleto.
  • Episodio: cambio rápido entre dos IDs invalida el modal previo.
  • Gestión de Camas: conectar, cerrar ventana temporal, consultar informe y olvidar sesión.
  • PDF: receta oficial, compacta, por profesional, externa y lote hospitalizados.
  • Solicitud: selección 2–3 órdenes, folios preservados y cero modificación clínica.
  • Turno/score: usar caso dummy autorizado y confirmar relectura/ACK/recovery.
  • Syslab: login oficial, búsqueda, selección múltiple, PDF, alertas, tendencias y rechazo de RUN distinto.
  • HHR: preview, conflicto de cama, alta administrativa, corrección histórica e idempotencia.
